# デザイナー不在の組織での運用

> 想定読者: メンバーの大半がエンジニアとマネジメントで、CSS や Web デザインを専門にする人がいない組織
> 本章の推奨は [2つの流派と選び方](03-two-styles.md) の実測データに基づきます

---

## その前に: DESIGN.md はデザインシステムではない

ここを取り違えると期待値がずれます。

仕様書自身は「デザインシステムの自己完結した表現」（`docs/spec.md:6`）と書いていますが、**表現することと、それであることは別**です。

デザインシステムは通常「トークン＋実装されたコンポーネント＋ドキュメント＋ガバナンス＋採用プロセス」の総体で、**成果物だけでなくそれを回す組織**を含みます。DESIGN.md はコンポーネントを1つも提供しませんし、実行時に何も強制しません。

**DESIGN.md はデザインシステムの「憲法」部分だけを切り出したものです。** 通常は Figma の表紙ページ、社内 Wiki の断片、そして口伝に散っている「なぜこうなのか」を、1ファイルの機械可読な形に固めたもの。

| | 答えること | 作るのに必要なもの |
|:--|:--|:--|
| デザインシステム | どんな部品があり、どう使うか | デザイン組織 |
| **DESIGN.md** | **何に見えるべきか、なぜか** | **良い記述** |

この差が、デザイナーのいない組織にとって決定的です。

---

## なぜ機能するのか

### 要求される入力が「デザイン能力」ではない

`PHILOSOPHY.md:48-52` の中心的主張は「**形容詞は領域を描き、具体的な参照は点を描く**」です。

ここで要求されているのは CSS の知識ではなく、**参照を1つ選ぶ能力**です。

- 「1970年代の大学講義ハンドアウト」
- 「駅の発車標」
- 「Bloomberg ターミナル」
- 「医療機器の操作パネル」

これらはエンジニアもマネジメントも普通に言えます。むしろ業務ドメインに近い人ほど、適切な参照を持っていることが多い。

**必要な入力が「デザインができる」から「何に似せたいか言える」に下がる。** これがこの種の組織にとっての本質的な価値です。

### 「ダメ出しする人の不在」を部分的に埋める

`PHILOSOPHY.md:56`:

> 十分に具体的な参照は、その制約を自動的に運ぶ。モデルは講義ハンドアウトが何であるかを知っており、**それが何でないか**も知っている。

デザイナーがいない組織の実質的な欠損は「作れないこと」より「**これは違う、と言える人がいないこと**」です。具体的な参照を1つ置くと、その禁止事項が自動的に付いてきます。

## 何が解決されないか

期待しすぎないために、限界を明示します。

### 出力を評価できる人は、依然としていない

**これが最大の弱点です。** DESIGN.md が改善するのは**入力**であって、出てきた UI を見て「違う」と言う工程は残ります。

しかも**ツールはそこを見ていません**。リントの11ルールのうち Markdown 本文に触れるのは `section-order` の1つだけで、それも**見出しの並び順しか見ません**。残り10個はすべてトークン検査です。`export` も全フォーマットで散文を捨てます。

つまり **「lint が通った DESIGN.md」は、デザインの良し悪しについて何も保証していません。**

ただし回避策が2つあります。

**回避策1: 参照が受け入れ基準を兼ねる**

「良いデザインか？」は非デザイナーには答えられませんが、
**「発車標に見えるか？」は答えられます。**

参照を具体的にしておくと、評価が「絶対評価」から「照合」に変わります。これは訓練なしで可能な作業です。**参照を曖昧にすると、この回避策ごと失われます。**

**回避策2: contrast-ratio は客観的**

WCAG AA（4.5:1）は主観が入りません。デザイナー不在の組織が機械的に守れる、数少ない品質指標です。CI に入れてください（[サンプル](../.github/workflows/lint.yml)）。

### 対象外の領域

- **コンポーネントは作りません。** MUI / shadcn / Bootstrap などは別途必要です
- **情報設計の誤りは検出しません**
- **「このボタンの位置がおかしい」は対象外です**
- **インタラクション設計**はデザイナーの代替になりません

## 運用手順

### 1. コンポーネントライブラリは捨てない

DESIGN.md は置き換えではなく、その上に載る意図の層です。既存の MUI なり shadcn なりはそのまま使ってください。

### 2. 流派B（散文のみ）で始める

**この章で最も重要な推奨です。**

トークンを書くには色・タイプスケール・余白を**決める必要があり、決められる人がいません**。Material Design や Tailwind の既定値をコピーすると、まさに `PHILOSOPHY.md` が警告する「凡庸な中心」に着地します。

実測でも、実在する74件のうち **10件は frontmatter を1行も持たない完全な散文型**です（spotify / tesla / starbucks / mastercard など）。正当な書き方であり、**値を発明せずに始められます**。

→ 詳細は [2つの流派と選び方](03-two-styles.md)

### 3. Overview の参照を1つ、合議で決める

**マネジメントを巻き込むべき唯一の判断です。** 「見栄えがすること」を気にしているのは彼らなので、ここに参加してもらう方が後の合意が早い。

参照を間違えると、**一貫して間違ったもの**が出続けます。逆に言えば、ここさえ合っていれば残りは自動的に整います。時間をかける価値があるのはこの1点だけです。

避けるべき例と、その言い換え:

| ❌ | ✅ |
|:--|:--|
| モダンでクリーン | 空港の発着案内板。情報が主役で、装飾は一切ない |
| 親しみやすい | 個人経営の書店の手書きポップ |
| プロフェッショナル | 医療機器の操作パネル。誤操作が許されない前提の明快さ |
| 高級感がある | 美術館の図録。紙の質感と余白で語る |

### 4. Don'ts を運用で溜める

**この種の組織に最も向いている工程です。**

人は「良いものを作る」より「**違和感を指摘する**」方が圧倒的に得意で、後者はデザイン教育を要しません。「これは違う」と思った瞬間に1行足す。それが蓄積すると次の生成物に効きます。

ただし `PHILOSOPHY.md:58` の警告も一緒に持っておいてください。

> 長くとりとめのない Don't リストは、記述が曖昧すぎた兆候であることが多い。

**Don't の量は Overview の失敗指標です。** 増えすぎたら足すのをやめて、参照の具体化に戻ってください。

### 5. `Known Gaps` を必ず書く

仕様には無いセクションですが、実物の **43/64件（67%）** が使っています。

```md
## Known Gaps

- **アイコン**: 未定義。エージェントは既存のストローク幅と角の処理から推測してよい。
- **データ可視化**: 未定義。色の割り当て規則が未決のため、チャートを作る場合は
  必ず人間のレビューを挟むこと。
- **モーション**: 意図的に持たない。このプロダクトはアニメーションを使わない。
```

**決められる人がいない組織では、未定義領域が最大の事故源です。** 書いていないとエージェントが毎回違うやり方で埋めます。「決まっていない」と明示するだけで、少なくともそれがチームに共有されます。

「未定義」と「意図的に持たない」を**区別して書く**のが要点です。前者は将来埋まる穴、後者は設計判断です。

### 6. CI に入れる

エンジニア組織の強みは、デザインレビューではなく**ゲートを運用すること**です。DESIGN.md はデザインガバナンスの一部を CI ゲートに変換できます。

```bash
npx @google/design.md lint DESIGN.md        # contrast 違反・壊れた参照
npx @google/design.md diff before.md after.md   # 回帰があれば exit 1
```

`diff` は**散文の変更を検出しません**。散文こそが本体なので、そこは人間が読む必要があります。

### 7. 固まった値だけ、後から frontmatter に移す

散文は追記できますが、**根拠のないトークンは一度書くと消しにくい**（誰かが参照し始めるため）。この方向の移行は痛みが少ないので、急がないでください。

移行時の注意: **トークンを足したぶんだけ散文を薄くしないこと。** 実物の中央値は「トークン268行 対 散文206行」でほぼ拮抗しています。

## 使わない方がいい場合

公平のために書きます。

**視覚的な意見がまったく無いなら、コンポーネントライブラリの既定値をそのまま使うのが正解です。** その場合 DESIGN.md が足すものはほとんどありません。

DESIGN.md が効くのは「**何らかの意見はあるが、それを実行できる人がいない**」ときです。

- 「うちのプロダクトが Consumer アプリみたいに見えるのは違う」
- 「情報密度が低すぎて、業務で使うと画面が足りない」
- 「毎回エンジニアごとに見た目が変わるのが気になる」

こうした違和感が組織に存在するなら、それを言語化して固定する器として機能します。違和感すら無いなら、まだ早い段階です。

---

## まとめ

| 効くこと | 効かないこと |
|:--|:--|
| 入力の要求水準が「参照選定」まで下がる | 出力を評価する工程は残る |
| 参照からネガティブ制約が自動的に付く | ツールは散文（＝本体）を検査しない |
| 未定義領域を宣言できる | コンポーネントは作らない |
| 一部のガバナンスを CI に変換できる | 情報設計・インタラクションは対象外 |

**要点をひとつ選ぶなら: 参照を1つ、具体的に決めること。** それが入力の質と受け入れ基準の両方を同時に決めます。

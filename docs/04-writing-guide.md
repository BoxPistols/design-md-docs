# 書き方ガイド

> 出典: 本家リポジトリの `PHILOSOPHY.md`。行番号は同ファイルのもの。
> **引用について**: `PHILOSOPHY.md` と `docs/spec.md` は英語で書かれています。本文中の日本語の引用は筆者による訳です。原文は本家リポジトリを参照してください。

DESIGN.md の品質は、**トークンの精度ではなく散文の具体性**で決まります。ここでは何をどう書けばエージェントに効くのかを、原典の主張と実例で整理します。

## 前提となる1文

`PHILOSOPHY.md:17`:

> **生成されたデザインの品質は、値の精度よりも、意図がどれだけ明確に記述されているかで決まる。**

`#1A1C1E` と書いても、モデルはそれが「なぜ黒でないのか」を知りません。「**純黒ではない、グラファイト寄りの温かいインク**」と書いて初めて、モデルはその色を borders や diagram strokes にどう展開すべきかを判断できます。

トークンは値を固定し、散文は**判断の仕方**を伝える。後者がないと、書いていない場面すべてでモデルが独自に判断します。

## 原則1: 形容詞ではなく、具体的な参照を書く

`PHILOSOPHY.md:48-52` の主張:

> 「1970年代の、古い伝統ある大学の大学院講義ハンドアウト」は完結した世界を喚起する。一色のインク、たっぷりの余白、読みやすいサイズのセリフ、装飾の不在。その一文が、十数個の数値より多くの有用な情報を運ぶ。値の背後にある**理由**を運ぶからだ。
>
> 「モダン、クリーン、信頼感、プレミアム」は何も喚起しない。モデルはそれらの語が指す領域の中心に何かを作り、結果は typically generic になる。
>
> **形容詞は領域を描き、具体的な参照は点を描く。**

### ❌ 効かない書き方

```md
## Overview

モダンでクリーンな、信頼感のあるプレミアムな UI。
ユーザーフレンドリーで直感的な体験を目指します。
```

これは何も制約していません。この文から作れる UI は無数にあり、そのどれもが「間違っていない」。だから毎回違うものが出てきます。

### ✅ 効く書き方

```md
## Overview

高級マット紙の質感 — 上質なブロードシート紙か、現代的なギャラリーの図録。
読者は開始5秒で「これは読み物であって、広告ではない」と判断する。

Architectural Minimalism（建築的な最小主義）と Journalistic Gravitas
（報道の重み）の交点。装飾は情報の邪魔をしない範囲でのみ許される。
```

「ブロードシート紙」「ギャラリーの図録」は、モデルが具体像を持っている**参照点**です。余白の取り方、書体の選び方、色数の少なさが、そこから自動的に導かれます。

### 参照の選び方

良い参照は「モデルが知っていて、かつ**視覚的に特徴が際立つ**もの」です。

| 効く | 効きにくい |
|:--|:--|
| 1970年代の大学講義ハンドアウト | レトロな感じ |
| 空港の発着案内板 | インフォメーショナル |
| 医療機器の操作パネル | プロフェッショナル |
| 同人誌即売会のカタログ | 親しみやすい |

「業界」ではなく「**具体的な物体・場面**」を指すのがコツです。

## 原則2: ネガティブ制約はタダで付いてくる

`PHILOSOPHY.md:54-58`:

> 十分に具体的な参照は、その制約を自動的に運ぶ。モデルは講義ハンドアウトが何であるかを知っており、**それが何でないか**も知っている。グローもグラデーションも使わない。列挙する必要がない。犬と名指せば、犬が鳴かないことも伝わる。

そして重要な指摘が続きます。

> **長くとりとめのない Don't リストは、記述が曖昧すぎた兆候であることが多い。**

**Don't の量は、Overview の失敗指標として使えます。** 「あれもこれも禁止」と書きたくなったら、まず Overview に戻って参照を具体化してください。禁止事項を並べるより早く解決することが多いです。

そのうえで、`PHILOSOPHY.md:58` は「強い参照 **＋** 意図的な Do/Don't リスト」の組み合わせを sweet spot としています。**参照から導けない、そのプロダクト固有の判断**だけを Don't に書く、という切り分けです。

### 良い Don't の例（原典 `PHILOSOPHY.md:60-84` より）

```md
## Do's and Don'ts

- **Don't** タイトルページにヒーロー要素を置かない。本物のハンドアウトの
  1ページ目は「コンテンツの1ページ目」であって、雑誌の表紙ではない。
- **Don't** 大見出しの下にイタリックのリード文を置かない。それは Substack の作法。
- **Don't** ページ番号やメタデータに色を付けない。バーミリオンは図版の中だけに棲む。
- **Don't** Bold を使わない。どこにも。
- **Do** バーミリオンを図版の内側に留める。外側での希少さが、内側での意味を作る。
- **Do** 控えめなサイズ差を信頼する。セクションタイトルは本文の約1.9倍であって、5倍ではない。
- **Do** ページに余白が残ることを許す。3分の2で終わるページは正しく、埋め足りないのではない。
```

注目すべきは、**それぞれが理由を伴っている**ことです。「Bold を使わない」だけでは、モデルは強調が必要な場面で困ります。「控えめなサイズ差を信頼する」という代替手段がセットで書かれているから、判断できる。

## 原則3: トークンは散文の参照点として置く

`PHILOSOPHY.md:23-40` が示す書き方です。**トークンを先に置き、散文がそれを `{参照}` で指す。**

````md
## Colors

```yaml
colors:
  paper: '#F4F0E4'
  ink: '#1E1A14'
  vermilion: '#C3402A'
  rule-gray: '#B8B0A2'
```

単一インク＋アクセント1色の体系。

- **Paper** {colors.paper} はキャンバス — 温かみのあるゼロックス用紙。決して純白ではない。
- **Ink** {colors.ink} はグラファイト寄りの温かい黒。すべてのタイポグラフィ、罫線、
  図版のストロークを担う。決して純黒ではない。
- **Vermilion** {colors.vermilion} は唯一のアクセントで、**図版とチャート注釈の内側にのみ**現れる。
  タイポグラフィには決して使わない。ページ番号にも、いかなるメタデータにも使わない。
- **Rule gray** {colors.rule-gray} はコンテンツ内部のヘアライン罫線専用
  （チャートのベースライン、テーブルの区切り）。ページ枠の装飾には使わない。
````

各色に対して「**何であるか / どこに使うか / どこに使わないか**」の3点が書かれています。これがトークンだけでは伝わらない情報です。

> **Tip:** frontmatter に書いたトークンを、セクション内で ` ```yaml ` フェンスとして再掲することもできます。パーサは両方を読んで統合します。散文のすぐ隣に値があると読みやすいので、実物でもよく使われる書き方です。

## 原則4: 未定義領域を宣言する

仕様には無いセクションですが、**実物の67%（43/64件）が `Known Gaps` を書いています**（→ [2つの流派](03-two-styles.md)）。

```md
## Known Gaps

- **アイコン**: 未定義。エージェントは既存の視覚言語（ストローク幅、角の処理）から
  推測してよい。決定したらこのセクションから Shapes に移す。
- **データ可視化**: 未定義。色の割り当て規則が決まっていないため、
  チャートを作る場合は必ず人間のレビューを挟むこと。
- **モーション**: 意図的に持たない。このプロダクトはアニメーションを使わない。
```

「未定義」と「意図的に持たない」を**区別して書く**のが要点です。前者は将来埋まる穴、後者は設計判断です。

トークン側では `omitted` で同じことができます。

```yaml
omitted:
  - section: rounded
    reason: "ブランドブックに角丸の定義が無いため"
```

## セクション別の書きどころ

| セクション | 書くべきこと | ありがちな失敗 |
|:--|:--|:--|
| **Overview** | 具体的な参照。対象読者。5秒で伝わる印象 | 形容詞の羅列 |
| **Colors** | 各色の役割・使う場所・**使わない場所** | 色名と16進数の対応表だけ |
| **Typography** | 各レベルの役割と、書体選択の理由 | サイズ表だけ |
| **Layout** | グリッドモデルと、余白のリズムの根拠 | 「8pxグリッド」とだけ書く |
| **Elevation & Depth** | 階層の表現手段。**フラットならその代替手段** | 影の定義だけ書いて、フラットな場合を書かない |
| **Shapes** | 形状言語と、その一貫性の根拠 | 角丸の数値だけ |
| **Components** | 状態（hover/active）と、その意図 | ベース状態だけ |
| **Do's and Don'ts** | 参照から導けない固有の判断 | 一般論（「WCAG AA を守る」等） |

`Elevation & Depth` は仕様が明示的に「フラットデザインの場合は、階層を伝える代替手段（境界線、コントラスト）を説明せよ」と求めています（`docs/spec.md:258`）。影を使わないから空欄、ではありません。

## チーム運用: レビュー観点

DESIGN.md の Pull Request をレビューするときのチェックリストです。

**内容**

- [ ] Overview に**具体的な参照**があるか（形容詞だけになっていないか）
- [ ] 各色に「どこに使わないか」が書かれているか
- [ ] Don't が長大になっていないか（＝ Overview が曖昧なサインではないか）
- [ ] Don't に理由または代替手段が添えられているか
- [ ] `Known Gaps` が更新されているか（穴が埋まったら消す、増えたら足す）
- [ ] トークンを足したぶん、散文も増えているか（→ 実物の中央値は約1.3:1）

**機械で確認**

- [ ] `npx @google/design.md lint DESIGN.md` が error 0
- [ ] `npx @google/design.md diff <before> <after>` で意図しないトークン削除が無いか
- [ ] [落とし穴](05-pitfalls.md) の回避策に従っているか（特に `lineHeight` の書き方）

**diff レビューのコツ**

`diff` はトークンの added / removed / modified と、findings の増減を JSON で返します。**回帰があれば終了コード1** なので CI に組み込めます。ただし**散文の変更は検出されません**。散文こそが本体なので、そこは人間が読むしかありません。

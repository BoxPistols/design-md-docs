> 再現手順は末尾。スクリプトは [`tools/measure.py`](../tools/measure.py)
> **引用について**: `PHILOSOPHY.md` と `docs/spec.md` は英語で書かれています。本文中の日本語の引用は筆者による訳です。原文は本家リポジトリを参照してください。

このページだけは、仕様書の要約ではなく**実測**です。「どう書くべきか」を決める前に、世の中で実際どう書かれているかを知っておくと迷いが減ります。

## 結論から

実在する DESIGN.md は、**2つの流派にきれいに分かれます**。

| | 流派A: **スキーマ型** | 流派B: **散文型** |
|:--|:--|:--|
| 件数 | 64 / 74 | 10 / 74 |
| frontmatter | あり（中央値 268行） | **無し** |
| セクション | `## Overview` `## Colors` …（仕様の正準名） | `## 1. Visual Theme & Atmosphere` 〜 `## 9. Agent Prompt Guide`（番号付き9本） |
| トークン比率 | 中央値 **57.7%** | **0%** |
| 例 | airbnb, apple, figma, notion, nvidia, linear.app | spotify, tesla, starbucks, mastercard, lamborghini |

流派Bは frontmatter を1行も持たず、**すべて散文**です。10件が10件とも、判で押したように同じ9セクション構成を採っています。

CLI の `lint` は流派Bも受理します（トークンが無いことへの info/warning は出ます）。**どちらも正当な DESIGN.md** です。

## 公式サンプルは実物の分布の外にある

ここが実務上いちばん重要な発見です。

同じ物差し（空行を除いた行数）で、本家リポジトリの `examples/` 3件も測りました。

```
実物74件（流派A 64件）   トークン比率  中央値 57.7%   範囲 48.1% 〜 68.2%
本家 examples/ 3件       トークン比率  中央値 80.4%   範囲 77.3% 〜 80.7%
                                                     ↑
                        実物の最大 68.2% < 公式の最小 77.3%  ← 重なりがゼロ
```

分布で見ると一目瞭然です。

```
トークン比率   実物64件            公式3件
  0-25%        0件                 0件
 25-50%        2件  ##             0件
 50-75%       62件  ############   0件
 75-100%       0件                 3件  ###
```

**散文の量に至っては、中央値で 206行 対 37行 — 5.6倍の開きがあります。**

| | トークン行数（中央値） | 散文行数（中央値） |
|:--|--:|--:|
| 実物64件 | 268 | **206** |
| 公式 examples 3件 | 144 | **37** |

つまり、**公式サンプルを手本にすると、実運用の水準から大きく外れた DESIGN.md ができます。**

### なぜこうなっているか

公式サンプル3件は、色数が**きっちり47個で一致**し、命名も `surface-container-lowest` / `on-primary-fixed-variant` / `inverse-on-surface` と、**Material Design 3 のトークン体系そのまま**です。Material Theme Builder 相当の出力をそのまま貼ったものと見られます。

これは仕様の思想に照らすと皮肉な状況です。`PHILOSOPHY.md` は繰り返しこう言っています。

> **散文こそが仕様の焦点である。トークンの値はコンテキストであって、レンダリング指示ではない。**（`PHILOSOPHY.md:21, 42`）

そして `PHILOSOPHY.md` 冒頭の模範例は、frontmatter が **`name:` 1行だけ**で、あとは全部プロースです。

哲学が推す姿（散文中心）、実物の実態（散文と同程度のトークン）、公式サンプル（トークン8割）— この3つが全部ズレている。**手本にすべきは公式サンプルではなく、実物の中央値です。**

## 仕様に無いセクションが定着している

正準8セクションに含まれないのに、**過半数が使っている**見出しが3つあります。

| セクション | 使用率 | 内容 |
|:--|--:|:--|
| **Responsive Behavior** | 51 / 64 | ブレークポイントと、各幅での振る舞い |
| **Iteration Guide** | 50 / 64 | **エージェントに修正を指示するときの手順** |
| **Known Gaps** | 43 / 64 | **まだ定義していない領域の明示** |

後ろ2つは仕様がまったく想定していない、**エージェント運用のための実務セクション**です。

- `Iteration Guide` — 「この方向で調整したいときは、まずここを見て、こう指示せよ」をあらかじめ書いておく
- `Known Gaps` — 「アイコンとイラストレーションは未定義。エージェントは既存の視覚言語から推測してよい」のように、**穴を穴として宣言する**

`Known Gaps` は特に効きます。書いていないと、エージェントは未定義領域を勝手に埋めて、しかもそれを毎回違うやり方で埋めます。「ここは未定義だ」と明示するだけで、少なくとも**未定義であることがチームに共有される**。

これは `PHILOSOPHY.md:86-110` の「フォーマットは仕様ではなくユーザーによって育つ」という主張が、実際に起きている証拠でもあります。

**チームで書くなら、この3セクションは最初から入れることを勧めます。** [テンプレート](../templates/DESIGN.md) には含めてあります。

## どちらの流派で書くべきか

### 流派A（スキーマ型）を選ぶ場合

- **トークンを他のツールに流したい** — `export` で Tailwind / CSS変数 / DTCG に出せるのは frontmatter のトークンだけです。流派Bからは何も出ません
- **機械で検証したい** — `lint` の11ルールのうち9つがトークン検査です。壊れた参照・WCAG コントラスト・未参照トークンの検出は、トークンがあって初めて効きます
- **既存のデザインシステムがある** — M3 / Tailwind / 自社トークンが既にあるなら、それを写す形になります

実務ではこちらが基本です。74件中64件がこちらなのも、多くが既存プロダクトのデザインシステムを持っているからでしょう。

### 流派B（散文型）を選ぶ場合

- **これから作る** — 値が決まっていない段階でトークンを書くと、根拠のない数字が固定化されます
- **ブランドの世界観が主で、実装が従** — 「1970年代の大学講義ハンドアウト」のような強い参照が中心にあるなら、トークンは後からでよい
- **エージェントに探索させたい** — 値を決め切らないことで、モデルに解釈の余地を残せます

### 現実的な進め方

**流派Bで始めて、固まったところから流派Aに移す**のが素直です。

散文は追記できますが、根拠のないトークンは一度書くと消しにくい（誰かが参照し始める）。逆方向の移行は痛みが少ないので、迷ったら散文からどうぞ。

ただし移行時は、**トークンを足したぶんだけ散文を薄くしない**こと。実物の中央値は「トークン268行 対 散文206行」で、**ほぼ拮抗**しています。トークンが増えたら散文も増やす、が実運用の姿です。

## 測定の再現手順

```bash
git clone --depth 1 https://github.com/VoltAgent/awesome-design-md.git /tmp/awesome
python3 tools/measure.py /tmp/awesome/design-md

# 本家の公式サンプルと比較する場合
git clone --depth 1 https://github.com/google-labs-code/design.md.git /tmp/designmd
python3 tools/measure.py /tmp/designmd/examples
```

測り方の定義:

- **トークン行数** = frontmatter 内の空行でない行
- **散文行数** = frontmatter 以降の空行でない行（見出し・箇条書きを含む）
- **流派の判別** = 先頭が `---` だけの行で始まる frontmatter ブロックの有無

行数はあくまで proxy です。YAML のネストが深いとトークン行数は膨らみますし、散文の質は行数では測れません。それでも**桁が違えば傾向は読める**、という前提で使っています。

コレクション側が更新されれば数値は変わります。上の日付時点の値として読んでください。

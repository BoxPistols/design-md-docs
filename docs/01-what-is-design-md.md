# DESIGN.md とは何か

> 検証時点: フォーマット `alpha` / CLI `@google/design.md` v0.4.0（2026-08）

## 一言でいうと

**コーディングエージェントに「ビジュアルアイデンティティ」を永続的に持たせるための、単一ファイル形式。**

仕様書自身の定義（`docs/spec.md:6`）:

> セッションをまたいでも、異なる AI エージェント・ツール間でも、スタイル上の判断が引き継がれることを保証する、自己完結したプレーンテキスト表現

## どのカテゴリの道具か

ここを取り違えると評価を誤ります。

**DESIGN.md は `CLAUDE.md` / `AGENTS.md` のデザイン版です。**
コード規約をエージェントに持続させるあの系譜に、視覚言語を載せたもの。

デザイントークンのフォーマット（DTCG / Style Dictionary / Theo）**ではありません**。仕様書は明示的に「Design Token JSON spec に着想を得た」と述べ（`docs/spec.md:12-13`）、そこから借りているのは**型付きトークングループと `{path.to.token}` 参照記法だけ**です。

```
                  対象               永続化の単位
CLAUDE.md    →   コード規約     →   プロジェクト
DESIGN.md    →   視覚言語       →   プロダクト/ブランド
DTCG         →   トークン値     →   ビルドパイプライン
```

## 何を解決しようとしているか

エージェントに UI を作らせると、**セッションごとに違うものが出てくる**。これが出発点の問題です。

「モダン、クリーン、信頼感、プレミアム」と指示すると、モデルはそれらの語が指す領域の中心に何かを作り、結果は毎回それなりに違う、そしてどれも凡庸なものになる。

DESIGN.md はこれを、**1ファイルに書いて持ち回れる形にした**ものです。人間が読めて、git で差分が取れて、エージェントが毎回読み直せる。

## 中心的な主張

`PHILOSOPHY.md:17` に、この形式の思想が1文で書かれています。

> **生成されたデザインの品質は、値の精度よりも、意図がどれだけ明確に記述されているかで決まる。**

ここから、一見不思議な設計判断が導かれます（`PHILOSOPHY.md:42`）:

> **トークンの値はコンテキストであって、レンダリング指示ではない。**
> 一般に、仕様の中でトークンの要件を定めることは受け入れないし、推奨もしない。

トークンフォーマットに見えるものが、トークンの厳密さを追求しない。理由は続く `:44` にあります — 「先行する言語やツールが積み上げた**数十年の仕事を再発明しない**」ため。

CSS も Tailwind も DTCG も既にある。DESIGN.md が担うのは、それらが担えなかった「**なぜその値なのか**」の方だ、という立て付けです。

## 何ではないか

| | |
|:--|:--|
| **DTCG の競合ではない** | 着想元であり、置き換えではない。相互運用は `export` で一方向 |
| **ビルドツールではない** | Tailwind v3/v4・CSS変数・DTCG への出力は**一方向**。往復しない |
| **実装の source of truth ではない** | エクスポート先はすべてトークンのみ。**散文は捨てられる** |
| **Figma と同期しない** | Figma variables から戻す経路は用意されていない |

最後の点は運用設計に効きます。DESIGN.md を「デザインの正」と決めるなら、Figma 側との同期は人力になります。

## 付属ツール

CLI が4コマンドを提供します。

| コマンド | 用途 | 終了コード |
|:--|:--|:--|
| `lint` | 構造検証。JSON で findings を返す | error があれば `1`、読めなければ `2` |
| `diff` | 2つの DESIGN.md を比較し、トークン差分と回帰を検出 | 回帰があれば `1` |
| `export` | Tailwind v3/v4・CSS変数・DTCG へ変換 | 成功 `0` / 不正な `--format` `1` / 読めない `2` |
| `spec` | 仕様書そのものを出力（エージェントのプロンプトに流し込む用） | — |

`lint` は11個のルールを走らせます。壊れた参照・WCAG コントラスト・未参照トークン・セクション順序などを見ます。詳細は [落とし穴](05-pitfalls.md) に、**何を見ていないか**も含めて書きました。

ライブラリとしても使えます。

```typescript
import { lint } from '@google/design.md/linter';

const report = lint(markdownString);
report.findings;      // Finding[]
report.summary;       // { errors, warnings, infos }
report.designSystem;  // パース済みの状態
```

## 現在の成熟度

フォーマットは `version: alpha`。仕様書自身が components について「**仕様は活発に進化中**」と断っています（`docs/spec.md:311`）。

実務上の意味は2つです。

1. **破壊的変更が来る前提で運用する。** DESIGN.md をリポジトリに置き、CLI のバージョンを固定し、更新時は `diff` で影響を見る
2. **仕様と実装がまだ一致していない箇所がある。** これは推測ではなく実測です → [落とし穴](05-pitfalls.md)
